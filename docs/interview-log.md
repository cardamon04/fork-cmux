# cmux Windows版 インタビュー回答記録

更新日: 2026-10-31

要求・要件の正本は[requirements.md](requirements.md)。以下はQ1〜Q14の質問・回答と、その時点の整理を保存した記録です。後から方針を変更する場合は、正本の要件と変更理由を更新してください。

### Q1 最初の完成版の対象

質問: 最初の完成版は、誰がどこまで使える状態を目指すか。

回答: 「自分用のWindows版（推奨）— 自分の普段の開発で使える状態を目指し、配布への対応は後で判断します。」

反映: RQ-004、RQ-005。

### Q2 優先する利用目的

質問: 普段の開発で、まず解決したい困りごとは何か。

回答: 「Mac版cmuxの使い方をWindowsでも続けたい — 今使っている、または気に入っているcmuxの機能・操作を再現することを優先します。」

反映: RQ-006。Mac版の利用経験や具体的な必須機能は、この回答だけでは未確定。

### Q3 Mac版の再現範囲

質問: 最初の完成版で、Mac版cmuxをどの程度まで再現したいか。

選択肢:

1. 普段使う機能と作業の流れを再現する。見た目やWindows向けのキー変更は許容する。
2. 見た目・配置・キー操作もできるだけ近づける。Windows向けの変更は必要最小限とする。
3. 本家の全機能をできる限りそろえる。ブラウザ自動操作やSSHなども含めて差を減らす。

回答: 「本家の全機能をできる限りそろえる — ブラウザ自動操作やSSHなども含め、機能の差をできるだけ減らすことを目指します。」

反映: RQ-007、RQ-008。「できる限り」の具体的な許容範囲と、比較対象の本家の版は未確定。

### Q4 ターミナルから利用する実行環境

質問: Windows版のターミナルから、どの環境を使えるようにしたいか。

選択肢:

1. WindowsのPowerShell、WSL2、SSH先のすべて。
2. WSL2とSSH先が中心。Windowsネイティブのシェルは必須にしない。
3. WindowsのPowerShellとSSH先が中心。WSL2は必須にしない。

回答: 「PowerShell・WSL2・SSH先のすべて（推奨）— Windows上の開発、Linux環境での開発、リモート作業を一つのアプリで扱えるようにします。」

反映: RQ-009。

### Q5 クラウド・iPhone連携の範囲

質問: 本家のクラウドサービス連携とiPhone連携も、初回完成版の対象に含めるか。

選択肢:

1. どちらも初回の対象外。Windowsアプリ内の機能と、自分のWSL2・SSH先との連携をそろえる。
2. クラウドサービス連携まで対象。iPhone連携は後回しにする。
3. クラウド・iPhone連携の両方を初回の対象に含める。

回答: 「クラウド・iPhone連携も両方含める — 外部サービスや端末との連携まで含めて、本家との機能差を減らします。」

反映: RQ-010。これらを独断で後回し・対象外に変更しない。

### Q6 クラウド・iPhone連携の接続先と開発範囲

質問: クラウド・iPhone連携では、本家のサービス・公式iPhoneアプリをそのまま使うことを条件にするか。

選択肢:

1. 本家のサービス・公式iPhoneアプリとの連携を条件にする。独自サーバーや独自iPhoneアプリの開発は含めない。
2. 必要なら独自サーバー・独自iPhoneアプリの開発も含める。
3. 本家との連携を優先し、接続できないと判明した場合だけ、対象範囲を相談し直す。

回答: 「本家との連携を優先し、接続できない場合は範囲を再相談する — 今は両方を対象に残し、検証で制約が判明したときに着地点を判断します。」

反映: RQ-011。技術的な接続可否は未検証。独自サービスの開発を承認済みとして扱わない。

### Q7 機能比較の基準とする本家の版

質問: 本家と機能をそろえる際、どの時点の本家を比較対象にするか。

選択肢:

1. 要件確定時点の安定版に固定し、完成後に更新を追う。
2. 要件確定時点の開発版mainに固定し、その時点の最新機能まで対象にする。
3. 開発中も本家の最新機能を取り込み続ける。

回答: 「開発中も本家の最新機能を追い続ける — 追加機能も随時対象にし、完成時点での本家との機能差を減らします。」

反映: RQ-012。比較対象のコミットと機能差を検証ごとに記録する方法を検討し、最終の要件確認に含める。完成基準を勝手に固定版へ変更しない。

調査メモ: 2026-10-31に本家のreleases/latestを確認したところ、[v0.65.2.2](https://github.com/manaflow-ai/cmux/releases/tag/v0.65.2.2)へ転送された。比較対象の版としては未採用。

### Q8 日常利用の確認で必須とするAIエージェント

質問: 日常利用の確認で、必ず使いたいAIエージェントはどれか。選択肢以外も自由記述で追加できる。

選択肢:

1. CodexとClaude Codeの両方を必須検証対象にする。
2. Codexを必須検証対象にする。
3. Claude Codeを必須検証対象にする。

回答: 「CodexとClaude Codeの両方（推奨）— 両方について、対話、通知、セッション再開、対応する分割連携を確認します。」

反映: RQ-013。本家が対応するほかの機能・エージェントを対象外とする回答ではない。

### Q9 Windows版の画面とキー操作の方針

質問: Windows版の画面とキー操作を、どの方針にするか。

選択肢:

1. 画面構成は本家に近づけ、キー操作はWindowsに合わせる。
2. 画面とキーの配置を、Mac版にできる限り近づける。
3. 機能とCLIの互換性を優先し、画面・キー操作はWindows向けに別設計する。

回答: 「画面構成は本家に近く、キー操作はWindows向け（推奨）— サイドバーや分割の使い方は引き継ぎ、ショートカットはWindowsやシェルとの衝突を避けて割り当てます。」

反映: RQ-014。画素単位の外観一致や、Mac固有のキー割り当ての再現を要求する回答ではない。

### Q10 日常利用の検証規模

質問: 日常利用の合否を判断するとき、同時に開く作業の規模をどこまで想定するか。

選択肢:

1. AIエージェント4セッション、端末全体10ペイン程度。
2. AIエージェント10セッション、端末全体20ペイン程度。
3. AIエージェント20セッション、端末全体40ペイン程度。

回答: 「AIエージェント4セッション・端末全体10ペイン程度（推奨）— この規模で、入力・切り替え・通知が滞らず使えることを確認します。」

反映: RQ-015。10ペインを製品の最大数に制限する意図ではなく、日常利用の標準検証規模とする。

### Q11 導入と更新の方法

質問: 普段使いのための導入・更新は、どの状態を目指すか。

選択肢:

1. インストーラーで導入し、アプリから更新できる。設定を引き継ぎ、普段の利用では自分でビルドしなくてよい。
2. ZIPを展開して使い、更新時は手動で差し替える。アプリ内更新は必須にしない。
3. 手元でビルドして使い、更新時もビルドし直す。導入・更新の仕組みは後回しにする。

回答: 「wingetで導入できるようにしたい。」

反映: RQ-016。提示したインストーラー・ZIP・自己ビルドのいずれかを選択したとはみなさない。wingetの公開カタログ登録、個人用マニフェスト、更新方法の詳細は未確定。

### Q12 wingetの公開範囲と導入経路

質問: wingetの導入経路を、個人用の定義ファイルと標準の公開カタログのどちらにするか。

選択肢:

1. 個人用の定義ファイルを使う。`winget install --manifest <フォルダー>`で導入し、公開カタログへの登録は必須にしない。初回にローカル定義の利用許可設定が必要。
2. 標準の公開カタログへの登録を目指す。通常の`winget install --id <識別子>`や`winget upgrade`を使えるようにし、インストーラー・登録情報の公開も対象に含める。

回答: 「個人用の定義ファイルを使う（推奨）— winget install --manifest <フォルダー>で導入し、公開カタログへの登録は必須にしません。初回にローカル定義の利用許可設定が必要です。」

反映: RQ-017。初回の利用許可設定を導入手順に含める。通常の公開カタログ経由の`winget upgrade`が利用できるとはみなさない。

技術的な根拠: [Microsoftのinstall仕様](https://learn.microsoft.com/en-us/windows/package-manager/winget/install)、[パッケージ登録手順](https://learn.microsoft.com/en-us/windows/package-manager/package/)。公開登録の採用は、今回の要件整理中に実際の公開・申請を行う許可を意味しない。

### Q13 完成と判断する基準

質問: 完成とみなす基準を、どの厳しさにするか。

選択肢:

1. 普段使いでき、残る機能差・不具合をユーザーが了承したら完成。標準検証規模で通常の開発を1営業日行い、機能ごとの合否と残る差分を確認する。
2. 対象の全機能がそろうまで完成としない。普段の開発で使えるだけでなく、未対応機能をなくし、機能対照表の全項目が合格することを条件にする。

回答: 「対象の全機能がそろうまで完成にしない — 普段使いの検証に加え、Windows向けの同等機能も含めて未対応機能をなくし、機能対照表の全項目が合格することを条件にします。」

反映: RQ-018、RQ-019。普段使いができるだけ、一部の機能が動くだけ、未対応を一覧に書くだけでは完成とみなさない。クラウド・iPhone連携に制約が判明した場合は、RQ-011に従って相談する。

### Q14 winget導入後の更新方法

質問: wingetで導入した後の更新は、どの方法を必要とするか。

選択肢:

1. 新版の定義ファイルを使い、winget経由で更新できればよい。設定と保存済み作業状態を引き継ぎ、アプリ内自動更新は必須にしない。
2. wingetでの導入に加え、アプリ内の更新確認・自動更新も必要。本家に近い更新の使い方を実現する。

回答: 「アプリ内の更新確認・自動更新も必要 — wingetで導入できることに加え、本家に近い更新の使い方まで実現します。」

反映: RQ-020。個人用winget定義の提供だけで、更新の要件を満たしたとみなさない。

### Q15 要求と要件の最終確認

質問: 保存した要求・要件を、この内容で確定してよいか。補足案の「まず現在のWindows PCを動作保証対象にする」「普段使いの検証を1営業日行う」「本家mainの最新機能を追う」も含む。要求・要件の確定であり、Windows版の実装や動作検証はこれからである。

選択肢:

1. この内容で確定する。保存した要求・要件と補足案を、今後の設計・実装・完成判定の基準にする。
2. 修正してから確定する。変更点や不足を反映してから確定する。

回答: 「この内容で確定する（推奨）— 保存した要求・要件と補足案を、今後の設計・実装・完成判定の基準にします。」

反映: 要求・要件の状態を「確定」に更新。RQ-021〜RQ-023として、現在のWindows PCを対象とすること、1営業日の普段使い検証、本家mainを比較元とすることを明記。要求・要件の整理は完了し、製品の実装・技術検証は未着手として引き継ぐ。
